# Create 机械手（Deployer）性能分析笔记

日期：2026-09-17 · 依据：Create 6.0.10 官方源码 `DeployerBlockEntity.java`（mc1.21.1/dev 分支）

## 结论速览

机械手本身**不是**性能黑洞。待机开销接近零，成本集中在每次"激活"动作，而激活频率由**转速**直接决定。真正需要警惕的是它通过 FakePlayer 触发的 NeoForge 事件广播，以及整合包里其他模组对这些事件的监听开销。

## 逐项拆解

### 1. 待机每 tick 开销 ≈ 0

`tick()` 开头连续 early-out：

- `getSpeed() == 0` → 直接返回（不转动的机械手零成本）；
- `timer > 0` → 只做一个减法就返回。

也就是说机械手在两次激活之间的每个 tick 只做一次整数比较和减法。

### 2. 成本集中在每次激活

一次完整循环 WAITING → EXPANDING → RETRACTING 中真正花钱的操作：

- `start()`：一次方块射线检测（`level.clip`），很便宜；
- `DeployerHandler.shouldActivate(...)`：对目标位置做实体扫描（AABB 查询）——每次尝试激活都跑；
- `activate()` → `DeployerHandler.activate(...)`：通过 `DeployerFakePlayer` 模拟玩家右键/左键，**触发 NeoForge 事件总线**（`PlayerInteractEvent`、`AttackEntityEvent`、方块破坏进度等）。

### 3. "机械手卡"的真正来源：事件广播

假玩家交互会把事件广播给**整个整合包**——所有订阅了 `PlayerInteractEvent` 等事件的模组（圈地、权限、任务书、统计、日志……）的监听器都会跑一遍。单机模组数量越多、监听器越重，单次激活越贵。这不是 Create 自己能优化的部分。

### 4. 频率由转速决定

```
timer 初值 1000，每 tick 减去 clamp(|rpm| × 2, 8, 512)
```

| 转速 | 每次激活间隔 | 激活频率 |
|---|---|---|
| 32 rpm | ~16 tick | ~4 次/秒 |
| 128 rpm | ~4 tick | ~13 次/秒 |
| 256 rpm | ~1.5–2 tick | ~25+ 次/秒 |

性能杠杆是**转速**而非机械手数量：10 个低速机械手往往比 1 个 256 转的便宜。

### 5. 与其他设备的对比

- **机械臂（Mechanical Arm）**：每 tick 轮询其全部交互点（`searchForItem`/`searchForDestination` 遍历 inputs/outputs 列表，查询物品 handler）。交互点越多越贵，且是**每 tick 固定开销**，不像机械手可以靠低转速摊薄。
- **航空箱模组的共振器（修复前）**：每蛙港每 tick 扫描 31³ ≈ 3 万格——比上述两者贵几个数量级，已在 2026-09-17 的修复轮中处理。

## 对航空箱模组的意义

- 交互舱口的挤奶/剪毛/屠宰是**纯数据记录操作**（不生成实体、不扫描世界），单次激活开销极低；配合本轮加入的挤奶/剪毛冷却，机械手路径的总开销可以压到接近零。
- 给玩家的建议：对交互舱口使用机械手时**用低转速**（32–64 rpm 足够，挤奶有冷却，快了也是空转）。
- 若日后仍想彻底绕开 FakePlayer 事件开销，方向是做一个专用动能"护理站"方块（定时器驱动、不走玩家事件），本轮不做。
